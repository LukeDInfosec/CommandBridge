## 2026-10-08 — READ THE VERDICT, NOT THE NARRATION (6.8.1)

Reported from a live engagement: sqlmap tested every technique against an
endpoint, found nothing, and ended with

    [WARNING] (custom) POST parameter '#1*' does not seem to be injectable
    [CRITICAL] all tested parameters do not appear to be injectable.

and Command Bridge printed

    [+] SQL INJECTION FOUND - DBMS: Unknown - PARAMETER: #1* - CRITICAL

Same disease as the timing bug in 6.8.0, in a part of the codebase the
6.8.0 rewrite never touched: a conclusion inferred from prose instead of
read from the tool's own verdict.

1. THE SQLMAP OUTPUT PARSER - new modules/scanner/../sqlmap_verdict.py

   Two causes, both reproduced in tests/test_coffee_break.py:

   a) core/output.py flagged a finding on any line containing the substring
      "stacked queries". sqlmap prints

          [INFO] testing 'Microsoft SQL Server/Sybase stacked queries (comment)'

      while ANNOUNCING a test it is about to run. Every sqlmap run that got
      as far as the stacked-queries phase - nearly all of them - was
      therefore reported as a confirmed critical SQL injection.

   b) "[CRITICAL]" was read as a vulnerability severity. In sqlmap it is a
      log level, and the line it appears on most often is the one saying
      nothing was injectable.

   modules/sqlmap_verdict.py now parses the whole run at the end and reads
   only what sqlmap actually concluded: the "sqlmap identified the following
   injection point(s)" block, and the Parameter/Type/Title/Payload fields
   inside it. Negative statements are authoritative and clear the state.
   A line matching NARRATION (an INFO/DEBUG line that is testing, checking,
   trying, loading...) is never evidence, however alarming its wording.

   Severity is earned from the verdict block's own Type/Title - stacked
   queries or file access make it CRITICAL, anything else confirmed is HIGH.
   Several runs appended to one output file are split and judged separately,
   so a failed attempt cannot suppress a real one or the other way round.

   A run that found nothing now SAYS SO ("sqlmap did not confirm SQL
   injection - nothing reported") and explains why. The old code had no way
   to say that, which is half of why it over-claimed.

   Streaming colour follows the same rule: only the verdict block is
   coloured, so a "testing ... stacked queries" line no longer reads as a
   finding before the summary even prints.

2. BROKEN ACCESS CONTROL ON PUBLIC PAGES - checks/access.py

   Found by scanning the new demo target: a first scan returned eight
   "broken access control" findings on /products, /search, /wp-login.php,
   /wp-json/ and the home page. _forced_browsing reported any page an
   anonymous request could fetch and that looked the same as the logged-in
   version - which describes every public page ever served.

   It now requires what the vertical check already required: either the URL
   is a privileged path, or the anonymous response carries the logged-in
   account's own data. Eight false positives became zero, and the real
   findings on the same target were unaffected.

3. IDOR SUPPRESSED BY A NAV BAR - checks/access.py _leaked

   The shared-listing guard vetoed whenever the challenger's own name
   appeared anywhere in the visible text. Almost every application prints
   the logged-in user's name in its own furniture ("Signed in as bob"), so
   the guard fired on every page and threw away the real IDORs with the
   listings - including one on the demo target that genuinely leaks one
   customer's order to another.

   _without_chrome() now establishes the furniture empirically: fetch a page
   the challenger is plainly entitled to (their session-check URL) and treat
   every line of visible text on it as chrome. A shared listing still names
   both accounts in what remains; a leaked record no longer does. One extra
   request per identity per scan, cached on the Authenticator.

4. COMMAND INJECTION MISSED ON THE ENDPOINTS THAT USUALLY HAVE IT

   checks/injection.py skipped any result where the payload came back in the
   page, as an anti-reflection guard. But a diagnostic endpoint prints the
   command it ran AND THEN its output:

       $ ping -c 1 -W 1 127.0.0.1; echo CB4F2A91
       ping: not found
       CB4F2A91

   so the payload is always in the body and the check always skipped - on
   exactly the kind of endpoint command injection lives on. _without_payload()
   strips every literal copy of the payload (plus its HTML-escaped and
   URL-encoded forms) and then looks for the expected output in what is
   left. Reflection is still caught; execution is no longer thrown away.

Verified end to end against the new vulnshop target (see below): 9 findings,
all genuine, no false positives, and both planted decoys correctly silent.
All four suites pass (test_scanner 284, test_coffee_break 308,
test_coffee_chain 13, test_gui_smoke 242 - 847 assertions).

A NOTE ON THE DEMO TARGET

A deliberately vulnerable application was built alongside this release to
test against, and every fix above except the sqlmap one was found BY it
rather than reported from the field. It is a separate deliverable
(vulnshop/) and is not part of this repository. It has working SQL
injection, command injection and path traversal, binds to loopback, and
refuses any other address without an explicit flag. Two of its endpoints are
deliberately NOT vulnerable - a latency-scaling endpoint with no database
behind it, and a parameterised twin of the injectable product page - so a
scan of it tests the false-positive half as well as the detection half.


## 2026-10-02 — EVIDENCE DECIDES, NOT THE DETECTOR (6.8.0)

Reported from a live engagement: SQL injection raised as "[CONFIRMED]
CRITICAL" on `header 'X-Original-URL'` on the strength of a stopwatch alone —
a 3.43s baseline, a 5s payload that took 4.59s, a 10s payload that took 8.58s.
On an application that is slow, loaded or behind a proxy that is not evidence
of anything. The fix is not wording: no check is allowed to declare its own
confidence any more.

1. A NEW MODULE GRADES EVIDENCE — modules/scanner/grading.py

   Evidence has grades, ordered by how hard each is to explain away: an
   out-of-band callback, command execution, backend-derived data, an
   engine-specific error signature, a reproduced behavioural differential, an
   executable context, a plain observation, a response-time anomaly, a
   reflection, and "the application accepted the input" (which proves
   nothing). POLICY maps each issue class to which grades are decisive for it,
   which merely support, and which can NEVER confirm it however many are seen.

   grade(issue, signals) -> Verdict. The rules, in order: a decisive signal
   confirms — except a differential, which must have been REPRODUCED, because
   one pair of responses that differ is what a page with a timestamp in it
   looks like; evidence drawn only from the class's "never" list is capped at
   Potential, since three stopwatch readings are one stopwatch reading; two
   independent supporting signals make it Likely; one makes it Potential;
   nothing usable is Inconclusive.

   Four levels: confirmed / likely / potential / inconclusive. Every Verdict
   carries its rationale, its limitations (what could explain the observation
   without the vulnerability) and the verification step that would settle it.

   For sqli, timing and reflection are both on the "never" list. The field
   scenario above now reports POTENTIAL with the raw measurements preserved.

2. EVERY ACTIVE CHECK WAS REFACTORED, NOT JUST SQL INJECTION

   ScanFinding gained .signals, .verdict, .measurements, .auth_context and
   .method, plus .add(signal) and .settle(); .confidence is derived by
   settle() and is never assigned by a check. The hard-coded
   confidence="confirmed" is gone from every check in the scanner.

   - sqli.py: new METADATA_PROBES — eight read-only expressions (MSSQL
     CONVERT(int,@@version)/DB_NAME(), MySQL EXTRACTVALUE, PostgreSQL
     CAST(version() AS int)/current_database(), Oracle UTL_INADDR, SQLite
     load_extension) each with an extraction regex, tried ONLY once another
     channel has already fired, so a clean endpoint is never sent them.
     Database-derived data and engine errors now outrank the stopwatch, and a
     timing observation contributes measurements and nothing else. Nothing is
     dumped: one version string or database name is the whole of it.
   - injection.py: SSTI, code injection and command injection confirm on
     EXECUTION — a real command's output carrying the random marker — and a
     sleep that worked attaches a TIMING signal only.
   - xss.py: reflected and stored both attach REFLECTION plus
     EXECUTABLE_CONTEXT, and EXECUTION only when the browser actually ran the
     payload. Without a browser, XSS does not reach confirmed.
   - files.py: traversal and file inclusion confirm on DATA (file contents),
     open redirect on OBSERVATION (where the browser was actually sent).
   - access.py: both halves now re-ask the question serially before reporting
     (_repeats), so a differential caused by a cache, a race or a server
     truncating under a concurrent scan is not confirmed.

   Declared but NOT IMPLEMENTED, and now said so in the module and in the
   report header: SSRF, XXE and unsafe deserialization have policies so an
   imported finding is graded by the same rules, but the Active Scan has no
   detector for them and will never raise one.

3. SEVERITY AND CONFIDENCE ARE TWO STATEMENTS (§18)

   Severity says how bad it is if real; confidence says how well it is
   evidenced. Neither scales the other. grading.severity_label() and
   cb_evidence.severity_label() print the relationship instead of hiding it:
   "Potentially Critical", or "CRITICAL if real" when inconclusive. The
   findings table keeps them in separate columns with separate palettes, so a
   confirmed low and a potential critical cannot look alike at a glance.

4. RAW DETECTION IS KEPT APART FROM THE INTERPRETED FINDING (§17)

   cb_evidence.detail_html(), report.as_markdown(), report.as_html() and
   report.as_json() all show the graded signals and their raw measurements in
   their own labelled section FIRST, then the interpretation, then what could
   explain it without the vulnerability, then — for anything short of
   confirmed — how to confirm it. The JSON carries raw_detection.signals and
   raw_detection.measurements so a consumer can re-judge the evidence itself.

5. ONE PLACE RECONCILES THE GRADE WITH THE EVIDENCE CHAIN

   cb_evidence.assess_scan() now reads the scanner's graded verdict instead
   of asking "did the detector say confirmed". The grade governs in both
   directions — it can confirm and it can hold a finding down — and it can
   never lift one above what its evidence chain supports. Its rationale,
   limitations and verification advice are carried into the Validation, so
   the Findings pane, the Markdown report, the HTML report and the JSON
   cannot disagree about a single finding. coffee_break.finding_from_scan()
   goes through the same function.

6. AUTHENTICATION CONTEXT ON EVERY FINDING (§15)

   grading.auth_context() records whether the scan was authenticated, by
   which method, as which identity, which verification URL proved it, and
   whether the session was ever verified or was lost mid-scan. Printed on
   every finding in all three formats: SQL injection on a public search box
   and the same injection behind an administrator login are not the same
   report.

Verified: SlowClean (3-4s jittery baseline, no bugs) -> no findings;
ErrorSqli -> CONFIRMED via backend-derived data and an engine error signature,
returning 'Microsoft SQL Server 2019 (RTM) - 15.0.2000.5'; BlindSqli ->
CONFIRMED via a reproduced behavioural differential; TimingMimic (latency
scales with a number in the input, no SQL anywhere) -> no findings at all: the
stability gate rejected it before grading, and had it been raised the ceiling
for timing-only evidence is POTENTIAL. All four suites pass
(test_scanner 284, test_coffee_break 288, test_coffee_chain 13,
test_gui_smoke 242).


## 2026-10-02 — THE LIGHT AND THE REPORT TELL THE SAME STORY (6.7.1)

Reported from a live engagement: the indicator showed a green "Authentication
Successful" while the finished report said (UNAUTHENTICATED), the login
genuinely failed against an ASP.NET portal with correct credentials, and the
findings list filled with HIGH "broken access control" on jQuery. Three bugs,
reproduced against a portal built to match the log that was sent in.

1. THE LOGIN FAILED BECAUSE THE SUBMIT BUTTON WAS NEVER SENT

   _read_login_form() read `<input>` elements only, and inside those it
   skipped type="submit". ASP.NET MVC controllers routinely branch on the
   submit control — `Command=Login` — to tell a login POST from any other
   POST to the same URL. Without it the controller never treats the request
   as a login, re-renders the page, and the scanner reports refused
   credentials against credentials that are fine. The log said so exactly:

       [AUTH] Login response: HTTP 200 at https://example.com/
       [auth] AUTHENTICATION FAILED — the login request returned the login
              page again

   FIXED. The parser now reads what a browser would send: `<button>`
   (the modern spelling of the same thing), `<select>` and `<textarea>`
   defaults, ticked checkboxes, and the FIRST submit control's name and
   value — first only, because a browser sends the button that was clicked
   and a form with "Log in" and "Forgot password" must not send both.

2. A GUESS WAS OVERRULING THE EVIDENCE

   _login_form() decided the login had failed from the shape of the login
   response and returned False — BEFORE check_session() had ever requested
   the verification URL. On a portal whose home page carries a login widget
   beside its content, or which renders the dashboard at the same path, a
   completely successful login was reported as refused.

   FIXED. The login response is now a signal, not a verdict. What it looked
   like is recorded; the verification URL decides. The heuristic only has the
   final word when there is no verification URL to consult — the one case
   where a guess beats nothing. When the two disagree, both are reported:
   a refused login now reads "the application replied 'Invalid username',
   and the session signature 'Sign out' was not in the response" rather than
   only the second half.

3. WHY THE LIGHT AND THE REPORT DISAGREED, AND WHY jQUERY WAS "HIGH"

   One line in send():

       self.logged_in = retried is not None and self.looks_logged_in(retried)

   `logged_in` is what AccessControlCheck reads to decide whether there is a
   real session to compare an anonymous one against. Setting it from whether
   one arbitrary response looked logged-in meant an entirely unauthenticated
   scan could flip it true — and then the check compared an anonymous session
   against an anonymous session, found every page 100% identical, and
   reported the whole crawl as broken access control. Including jQuery.

   The same line reset _consecutive_lapses, which re-armed the three-strikes
   test, which is why the log showed "session lapsed — logging back in
   (attempt 7)" long after the scanner had announced it was giving up.

   FIXED
     * `logged_in` is set only by check_session() — the verification URL —
       and never by a single response's appearance.
     * _gave_up is now a hard stop. A login refused at the start is never
       retried at all (_relogins goes from 7 to 0 on the reproduction).
     * ScanResult.authenticated is DERIVED from the outcome rather than
       tracked separately, so the report line and the indicator are the same
       fact read twice and cannot drift.
     * Authenticator.on_state_change publishes every change, so the indicator
       follows the session for the whole run. A session that dies forty
       minutes in now shows "Session Lost During Scan" while it is happening
       instead of being inferred afterwards from an empty report. That is a
       new state, distinct from "failed": a login that never worked is a
       configuration problem, a session that died is a timeout or a
       concurrent-login policy, and the findings up to that point are real.
     * AccessControlCheck additionally refuses to run unless the outcome
       itself says ok/unverified, and skips static assets outright —
       .js/.css/fonts/images and the directories that hold them. jQuery is
       meant to be readable without a session.

TESTS — 251 scanner / 236 GUI / 288 Coffee Break / 13 chain. The new section
  runs a real ASP.NET-shaped portal: anti-forgery token, login form on the
  home page, POST to the same URL, 200 either way, and a controller that
  branches on the button. It asserts the login succeeds, that a genuinely
  refused one still fails with the application's own words, that the
  indicator and the report agree in both cases, that a mid-scan session loss
  is reported as a loss, and that nothing static is ever an access-control
  finding.


## 2026-10-01 — PROVE IT, THEN HAND IT OVER (6.7.0)

Three things a tester asked for, all of them about the same thing: a finding
you can put in front of a client without doing the work again yourself.

COMMAND INJECTION IS PROVED BY OUTPUT, NOT BY WAITING

  The old check led with arithmetic and fell back to a timed sleep, and the
  sleep was doing most of the work. On an application that is slow — or slow
  in proportion to how much a request asks it to do, which is most real
  applications — a scaled delay happens without any injection, and a finding
  that says "this took 9s instead of 4s" is not something that goes in a
  report. It is a job for the person reading the report.

  checks/injection.py now works in two phases:

    1. ESTABLISH EXECUTION. A random token through `echo`, platform-neutral
       and cheap. Confirmed only when the token appears, the payload does
       NOT appear (reflection is not execution), the token is not sitting
       beside the word that printed it, and the token was not already in the
       baseline.
    2. MAKE IT TALK. Only once a separator is known to work does the check
       spend requests on `id`, `whoami`, `uname -a`, `pwd`,
       `cat /etc/passwd` — and on Windows `whoami`, `ver`, `dir C:\`,
       `type win.ini`. Each is its own evidence step with its own request and
       response, so the report shows the command and the output side by side.
       That is the screenshot.

  oracles.command_output() holds the signature table — `uid=0(root) gid=…`,
  `root:x:0:0:`, `Microsoft Windows [Version …]`, `[fonts]` and the rest. A
  match is discarded if it is also in the BASELINE body (an application whose
  own documentation shows /etc/passwd must not be reported for quoting
  itself) or inside the payload (we are reading our own input back).
  WEAK_SIGNATURES — `whoami`, `pwd` — corroborate and never confirm on their
  own: a bare word and an absolute path match ordinary page text far too
  easily.

  TIMING IS DEMOTED, NOT REMOVED. When it fires, the check immediately tries
  to turn it into real output through the same separator; success upgrades
  the finding to a confirmed one with the command output attached. Failure
  means:
    * confidence "tentative", not "confirmed", so the evidence layer renders
      it POTENTIAL / manual validation required rather than a confirmed
      CRITICAL; and
    * it is not reported at all unless Profile.report_timing_only is on,
      which is a new checkbox in Scope and aggression, OFF by default.
  oracles.Timing also sends a ZERO-SECOND control now. If asking for a
  0s sleep also takes several seconds, the delay was never ours. That one
  extra request removes the commonest false positive on a laggy target.

  Blind injection is still reported, and the detail says plainly that the
  command runs but the page does not show it, rather than implying there is
  output to screenshot.

COPY BURP REQUEST

  Evidence.request was always a human summary — "GET http://host/path?id=1"
  — which is not a request Burp accepts. burp_request() used to fall back to
  it, which meant the button pasted something that looked right and came back
  400.

  * model.raw_http(prepared) renders the PreparedRequest `requests` ACTUALLY
    SENT as raw HTTP/1.1: origin-form request line, Host, every header with
    the session's cookies already merged, recomputed Content-Length, blank
    line, body. Reconstruction (raw_http_from_request) is the fallback for
    the few steps that never got a response, and reads cookies and defaults
    off the live session so the block is still complete.
  * model.step(label, request, response, auth=…) builds every evidence step
    and captures the wire form AT THE MOMENT IT IS SENT. All five check
    modules now go through it, so no finding can be recorded without its
    request — the button works for every check rather than for whichever
    ones remembered.
  * Evidence.raw_request carries it; burp_request() returns that and NOTHING
    ELSE. No raw request means no button, and the button says
    "No request captured for this finding" rather than copying an empty
    clipboard.
  * "Copy Burp Request" sits under the detail pane on BOTH findings screens.
    Confirms in the button text for two seconds; no dialog, because a tester
    presses this thirty times in an afternoon.
  * The PoC for command injection now LEADS with a request that returns
    output (`id`, `cat /etc/passwd`) rather than the token echo, and
    evidence_from_scan takes the payload from the LEAD step so the payload
    printed above a request is the one inside it.

THE SECOND ACCOUNT HAS A DECLARED ROLE

  "Account B saw account A's page" is a data leak between peers and a
  privilege escalation between levels. Same observation, different finding,
  and the scanner cannot tell which. So the operator declares it:

    Same level     → horizontal (IDOR). Needs an object identifier AND the
                     first account's data in the second's response.
    Lower          → vertical (privilege escalation). Crawls as the admin,
                     replays as the restricted account. Privileged paths
                     (/admin, /manage, /users/…/roles, /billing) CRITICAL;
                     the rest HIGH.
    Higher         → the same test with the direction reversed, for when the
                     first account is fixed for another reason.

  A wrapped explanation sits under the dropdown and changes with it, saying
  which login goes in which box and what the scanner will do with it. In a
  tooltip this was being missed, and entering the two accounts the wrong way
  round silently inverts every finding the check produces.

  FALSE POSITIVES WERE THE WHOLE PROBLEM HERE. Most of an application is
  pages both accounts are meant to see; they come back 99% identical and the
  naive vertical test reports the entire site. The gate is now: a privileged-
  looking path, OR the privileged account's identifier genuinely leaking into
  the other's response. "Genuinely" does real work:
    * attribute values, <script> and <style> are stripped first
      (visible_text), because <input name="nick" value="alice"> is a form
      default, not alice's data;
    * a marker that came from OUR OWN request is reflection, not a leak;
    * a page containing the reader's own name too is a shared listing
      ("All users: alice, bob"), not a leak;
    * _owner_marker no longer falls back to the first email on the page — on
      a page showing somebody else's record that returned THEIR address as
      proof the record was ours, which inverts the one thing it exists to
      establish.
  Against the test application all three roles now report exactly the two
  planted access-control bugs and nothing else; /dashboard, /tools, /profile
  and /item_safe are all correctly silent.

  The vertical modes also run the horizontal test, since a second account
  proves whatever it proves whatever level it is. The IDOR test always runs
  in the crawl's direction: those URLs name the first account's records, so
  asking whether the first account can read its own is not a question.

TESTS — 218 scanner / 236 GUI / 288 Coffee Break / 13 chain, all passing.
  The command-injection and Burp assertions run against the REAL engine
  output, not a fixture. Two existing tests failed on this change because
  their hand-written fixtures had no raw_request; that is the tightening
  working, and the fixtures were corrected rather than the behaviour.


## 2026-10-01 — THE SCAN SAYS WHAT IT IS DOING (6.6.0)

AUTHENTICATION: WHY A GOOD LOGIN REPORTED "UNAUTHENTICATED". Reproduced
against a server that behaves like a real application. Three separate causes,
all in session.py:

  1. LOGGED_OUT_SIGNS treated `<input type="password">` as proof of a login
     page. Every account, profile and settings page in existence offers
     "change your password" — and those are exactly the pages a tester gives
     as the verification URL. A correct session on a reachable /my-profile
     was being read as logged out.
  2. verify_session() followed redirects. Once requests has followed a 302 to
     the login page the status is 200 and the only surviving clue is the
     body, so a redirect straight to /login looked like a healthy response.
  3. verify_session() fell back to the LOGIN URL when no check_url was given.
     Checking the login page for signs of being logged in can only ever
     answer "no".
  And separately: _login_form() never looked at the login response at all, so
  rejected credentials proceeded silently and the failure surfaced much later
  as a bare "unauthenticated".

FIXED

  * judge(response) -> (verdict, reason) replaces the old boolean heuristic,
    weighing evidence in order of what it proves: an explicit signature,
    401/403, an UNFOLLOWED redirect towards login, the final URL after
    redirects being a login page, logged-out prose, and only then form shape.
  * LOGIN_FORM_SHAPE matches a password field beside a username/email field
    IN THE SAME FORM. A change-password form has no username field and no
    longer counts. LOGGED_IN_SIGNS carry positive evidence.
  * check_session() never falls back to the login URL, requests without
    following first so a 302 is visible as a 302, and returns the reason.
  * _login_form() inspects the login response: rejected credentials and
    landing back on the login page are both caught at the point they happen.
  * AuthOutcome records every step, the method, the verdict and the reason.
    Three states, not two — 'ok', 'failed', and 'unverified' for when no
    verification URL was supplied, because claiming success for something
    nothing checked is the habit that caused this.
  * [AUTH] logging throughout. Passwords are never written: as_dict() masks
    them and no step line carries credential material.

UI (tabs_scan.py)

  * An authentication indicator beside Save report, driven by the
    authenticator's own verdict via a new on_auth callback that fires as soon
    as login resolves — not by whether the username box has text in it.
    Amber while checking, green Successful, amber Unverified, red Failed,
    with the reason on hover.
  * Progress carries live detail: the URL, the parameter and the check
    currently running, announced by _announce_check() as each check STARTS.
    The count reads as "27 of 268" while the 27th is being tested.
  * Discovered Parameters label with a click-to-open link.

Active_Scan_Discovered_Parameters.txt — written by the engine into the
output directory when a scan finishes, from the requests and insertion points
the scan actually used, so it cannot contain a URL the crawl never reached.
Methods, parameter names and example values preserved, de-duplicated, sorted,
split into tested and found-but-not-tested. Nothing written when nothing was
found. The Markdown report names the file and now carries the authentication
method and reason instead of a bare yes/no.

TESTS: 189 (scanner, +50) / 205 (GUI, +22) / 288 (coffee break) / 13 (chain).
The authentication block pins each of the three causes with the page shapes
that triggered them, asserts no password reaches the log, and covers pasted
cookies reaching the same states.


## 2026-10-01 — THE POC NAMES THE PAYLOAD (6.5.1)

FOUND BY RUNNING THE SCANNER FOR REAL. An authenticated scan of the test
application confirms nine findings including the SQL injection — and every
one of them rendered as "[POTENTIAL] ... Payload: NOT CAPTURED ... PoC
unavailable". The scan was right; the evidence layer added in 6.4.0 was
throwing the proof away.

Two causes, both mine:

  1. model.Evidence had no payload field. evidence_from_scan() recovered the
     payload by regex from the human-written label (`payload[: ]+(.+)$`), and
     the checks label their steps "Condition true — page returned as normal",
     "Injected with ';'" and so on. It never matched. The 6.4.0 test passed
     because its fixture was hand-written with the label "injected payload:
     ;id" — it tested the assumption, not the data.
  2. The lead evidence was items[0], which for a boolean SQL injection can be
     the FALSE control. A PoC headed by the request that deliberately did
     nothing is worse than no PoC.

FIXED

  * model.Evidence gains `payload` (what was sent) and `decisive` (the step
    that demonstrates the issue). Set throughout checks/sqli.py,
    checks/injection.py, checks/files.py and checks/xss.py; oracles now carry
    the payloads out of the differential and timing results rather than
    discarding them.
  * evidence_from_scan() takes the payload from the first step that records

  1. Coffee Break's Pause suspended the external tool (SIGSTOP) and held the
     chain, and that was all. The Python probe stages — headers, redirects,

     requests to the target after the operator had pressed Pause and walked
     away. Pause stopped the progress bar, not the traffic.

    wakes everything immediately. STOPPING ALWAYS WINS — a stopped gate never
    blocks, so a paused run can be shut down without being resumed first.
    That is what makes closing the window after a Pause safe rather than a
    hang.
  * wait() blocks while paused and returns False when the run should stop.
    With a timeout it returns False if still paused when time is up — the
    question is "may I send?", and while paused the answer is no however long
    the caller waits.
  * gate_session(session, gate) wraps requests.Session.request, so one

## 2026-09-29 — THE EVIDENCE CHAIN (6.3.0)

A finding may no longer claim anything its evidence does not support.

ROOT CAUSE OF THE CSP → CWE-78 REPORT. cb_issues.for_nuclei() classified a
nuclei result from `template-id + name + DESCRIPTION`. A template's
description is prose about the class of problem, written for a human. nuclei
ships weak-csp-detect with a description ending "…which can lead to arbitrary
code execution"; _TEXT_ISSUES matches `code execution` → command_injection
several entries before it reaches the `csp` pattern; so a
Content-Security-Policy header was published as CRITICAL / CWE-78 / "Input
reaches a shell", with `object-src 'none'` underneath it as the proof. Nothing
downstream could catch it, because nothing downstream ever compared the claim
against the evidence.

  * for_nuclei() now classifies from the template's IDENTITY only (id +
    name). The description is retained as metadata on the evidence object and
    is never consulted for classification. The parameter is kept in the
    signature and deliberately unused.

NEW MODULE: command_bridge/modules/cb_evidence.py

  * Evidence — one object per detection holding method, URL, endpoint,
    parameter, location, original value, payload, request, response, status,
    headers, body excerpt, baseline pair, comparison, timing, redirect, OOB
    interaction, detector, template id/name/author/severity/tags/path,
    matcher, extracted values, raw output, observation, timestamp and a
    correlation id. Deep-copied on every hand-off; never shared.
  * States — DETECTED / POTENTIAL / VALIDATED / CONFIRMED / INCONCLUSIVE /
    FALSE_POSITIVE. Confidence — informational / potential / low / medium /
    high / confirmed. Both are DERIVED from the evidence, never set by hand.
  * EVIDENCE_TOPICS + topics_in() — what a piece of evidence could possibly
    be about (csp, shell, sql, xss, tls, header, cookie, path, panel,
    disclosure, service, timing, oob).
  * CLASSIFICATION_TOPICS — what each classification is a claim about.
    Evidence sharing no topic with the claim is a classification conflict,
    reported in as many words and never suppressed.
  * EXPLOIT_REQUIRED + EVIDENCE_REQUIREMENTS — the injection/execution
    classes cannot be established by a signature, header or banner. They need
    an injection point, a payload and an observed consequence (or a validated
    OOB interaction). Missing pieces become false-positive indicators.

  * poc_section() / Evidence.poc() / burp_request() — a PoC is rendered from

verified against official docs/README/PRs for each:

  calibrate) — ffuf's own built-in fix. It probes the target with a few
  random/nonexistent paths before the real run, learns what that false-
  positive response looks like, and filters matching results automatically.
FFUF_CLEAN.PY BACKSTOP (modules/ffuf_clean.py): -ac's calibration samples
  are "obviously random junk" paths, which some servers treat differently
  from a real dictionary word that just isn't a real page — so as defense in
  depth, ffuf_clean.py now also groups all results by exact response byte
  length. If one length accounts for >= 5 results AND >= 25% of all results,
  those are pulled into a clearly-labelled "[FILTERED] N of M results were
  X bytes..." section at the bottom of the output instead of the main
  findings list — NOT deleted (kept for audit), just no longer buried among
  real findings. Verified against a synthetic 503-result JSON matching the

## 2026-09-15 (b) — Install/Repair Tools: fixed real-world failures from first run
Follow-up to the same day's batch below, after the user actually ran
"Install / Repair Missing Tools" on their real Kali box and hit 3 real
failures out of 10 (droopescan, uro, kxss) that the dev sandbox couldn't
have caught (no real pipx/go environment there). Both root-caused and fixed
in modules/install_tools.sh:
PIPX "--force" CRASHES ON A TRULY-BROKEN VENV (droopescan + uro both failed
  identically: `FileNotFoundError: [Errno 2] No such file or directory:
  '.../pipx/venvs/<tool>/bin/python'`, raised from pip's own subprocess.py
  during posix_spawn). This is a known long-standing pipx bug (pypa/pipx
  #146, #294): `pipx install --force` tries to reinstall IN PLACE and, as
  part of that, spawns the OLD venv's own python — which is exactly the
  interpreter that no longer exists after a system Python upgrade, so pipx
  itself crashes with an uncaught traceback instead of just rebuilding the
  venv. Rewrote pipx_install() to: (1) try `pipx repair <tool>` first — this
  is pipx's own purpose-built subcommand for exactly this scenario (rebuilds
  the venv from recorded metadata without needing the old interpreter to
  still exist), confirmed via pipx's official troubleshooting docs; (2) if
  that's unavailable (older pipx without `repair`) or doesn't fully fix it,
  manually `rm -rf` the broken venv directory and shim first, THEN run a
  plain `pipx install` (no --force) — a plain install of a target that no
  longer exists on disk can't hit the same in-place-reinstall codepath.
  Verified with a mocked `pipx` binary exercising both branches (repair
  succeeds; repair unsupported -> manual cleanup -> plain install succeeds).
  This also fixes every OTHER tool that goes through pipx_install() (arjun,
  graphql-cop, ghauri, graphw00f's pipx path), not just droopescan/uro.
KXSS WRONG GITHUB USERNAME: _i_kxss was pointed at
  `github.com/Emenalf/kxss` — that repo doesn't exist (a typo'd/incorrect
  username from the original research), which is why `go install` failed
  with a confusing "could not read Username for 'https://github.com':
  terminal prompts disabled" error (go's module resolution treats some
  GitHub 404s as "maybe private" and tries to prompt for credentials, which
  fails outright in a non-interactive shell). Corrected to the real repo,
  `github.com/Emoe/kxss` (verified via web search + fetching the repo's own
  README, which shows `go install github.com/Emoe/kxss@latest` verbatim).

 APP OVERVIEW

WHAT IT IS
  "Command Bridge v4" — a PyQt6 desktop GUI that automates a penetration tester's
  workflow by chaining external tools (nmap, testssl, ffuf, sqlmap, nuclei,
  whatweb, ike-scan, ssh-audit, gobuster/dirsearch, feroxbuster, etc.) behind

================================================================================
 ARCHITECTURE (how it fits together)
================================================================================

MIXIN COMPOSITION
  ui/window.py -> class CommandBridgeV4(QMainWindow, <all the mixins...>).
  Every feature is a Mixin class added to this one god-object. So `self` inside
  any mixin method can see EVERY other mixin's methods/attributes. When adding a
  feature, write a new Mixin and add it to the CommandBridgeV4 base list (line ~49).

KEY SHARED STATE (set in window.py __init__, ~line 79)
  self.target                 - primary target string (Target Setup tab)
  self.output_dir             - where all results/report files are written
  self.command_registry       - dict of editable command templates {button_id: cmd}
                                persisted via save_custom_commands()/load_custom_commands()
  self.runner                 - CommandRunner (QProcess). runner.output_ready ->
                                on_command_output; runner.finished -> on_command_finished
  self.console                - EnhancedConsole (the output terminal widget)
  self.tab_widget             - the QTabWidget; Console tab is index 5
  Externals state machine:
    self._externals_active     - bool, True while a workflow is running
    self._externals_phase      - "discovery"|"nmap"|"directory_enum"|"tls"|
                                  "web_recon"|"check-discovery"|None
    self._externals_context    - dict carrying everything for the current run
                                  (targets, live_hosts, web_assets, open_ports,
                                   web_tech, tls_issues, findings, admin_interfaces)

COMMAND EXECUTION FLOW (the core loop)
  1. A button handler builds a shell command string and calls
     self.runner.run_command(cmd, cwd=self.output_dir)   (widgets/runner.py).
  2. QProcess runs `/bin/bash -c "<cmd>"` (sqlmap uses `script` for a PTY).
     stdout+stderr merged -> runner.output_ready signal.
  3. on_command_output (core/output.py:258) receives text -> may post-process
     (nmap port highlight, gobuster/sqlmap formatting) -> console.append_ansi().
  4. On exit, runner.finished -> on_command_finished (core/output.py:400):
     prints summaries, refreshes file list, and ADVANCES STATE MACHINES:
       - Auto Scan       (if self._auto_scan_active)
       - Externals        (if self._externals_active -> _on_externals_command_finished)

CONSOLE COLOURING (widgets/console.py)
  append_ansi() strips ANSI then _apply_feroxbuster_colors() regex-colours lines:
    - Lines starting "[DANGEROUS]"  -> RED bold
    - Lines starting "[WARNING]"    -> ORANGE bold
    - "NNN/tcp open ..."            -> GREEN (nmap open ports)
    - ffuf/gobuster/dirsearch hits, sqlmap, "[✖]"/"[✔]" -> coloured
  append_html() inserts raw HTML (used for custom coloured summaries).
  => To make console text red/orange, prefix the line with [DANGEROUS]/[WARNING],
     or build HTML and call console.append_html().

BACKGROUND WORK
  Long/blocking jobs run in a QThread with a QObject worker that emits
  progress(str) + finished(dict). Pattern used by: _SslScanWorker,
  _HttpAnalysisWorker, _NmapAllHostsWorker, and the new _ExternalsWebReconWorker.
  Keep a ref on self (e.g. self._extrecon_thread) so it isn't garbage-collected.

EDITABLE COMMANDS
  Many buttons store their command template in self.command_registry under a
  button_id and expose a right-click editor. See core/commands.py
  (run_command_template, open_command_edit_dialog) and the Externals editors
  (externals.py: show_externals_button_editor, _open_externals_workflow_editor).

================================================================================
 EXTERNALS WORKFLOW — STATE MACHINE (how a full run flows)
================================================================================

Trigger: Externals tab -> "Run Externals Test" -> run_externals_workflow()
Driver:  on_command_finished (core/output.py:400) calls
         _on_externals_command_finished(exit_code) after each QProcess command,
         which switches on self._externals_phase.

Phases (self._externals_phase):
  "discovery"     nmap -sn host discovery -> live_hosts.txt / unreachable_hosts.txt
                  -> sets phase "nmap"
  "nmap"          fast top-ports scan + full -sV -sC -O scan
                  -> _externals_process_nmap_results (open_ports, web_tech, dangerous,
                     http_hosts, tls_hosts)
                  -> dangerous summary + GROUPED dangerous_services.txt +
                     open_ports_by_service.txt + findings
                  -> _externals_run_security_headers (missing_security_headers.txt +
                     findings)
                  -> web_facing_hosts.txt (stored in context["web_assets"])
                  -> if web assets & user says Yes: phase "directory_enum"
                     else: _externals_start_tls_phase
  "directory_enum" ffuf over web_facing_hosts.txt (adaptive wordlist) ->
                     directory_findings.txt -> _externals_start_tls_phase
  "tls"           per-host `testssl` (sequential QProcess). Aggregates issues into
                  context["tls_issues"] -> externals_tls_summary.txt. When done:
                  -> _externals_begin_web_recon()
  "web_recon"     (QThread, not QProcess) _ExternalsWebReconWorker does active HTTP
                  recon. record TLS findings + tls_findings.txt first. On finish:
                  -> _on_externals_web_recon_done -> potential_admin_interfaces.txt,
                     technology_fingerprints.txt, additional_external_checks.txt
                  -> _externals_finalize_assessment()
  finalize        tally severities, write technical_findings.txt /
                  executive_summary.txt / external_assessment_summary.txt /
                  external_findings.json, print "ASSESSMENT COMPLETE", reset state.

  "check-discovery" is the separate, standalone "Check What's Up" path (discovery
                  only -> up.txt; no full run).

FINDINGS / SEVERITY MODEL
  Add a finding anywhere with: self._externals_add_finding(SEV, title, target,
  detail, evidence).  SEV in CRITICAL/HIGH/MEDIUM/LOW/INFO.
  Ports in CRITICAL_EXPOSURE_PORTS (redis, mongo, elastic, docker/k8s api, vault,
  consul, memcached, couchdb, ...) escalate to CRITICAL automatically.


================================================================================
 CONVENTIONS & GOTCHAS (read before editing)
================================================================================

- LINUX RUNTIME: commands are `/bin/bash -c` strings. Use Linux paths/tools. Guard
  optional tools with `if command -v TOOL >/dev/null 2>&1; then ... else echo ...`.
- CAN'T RUN GUI ON WINDOWS: validate with `python -m py_compile <file>`. For logic,
  stub PyQt6.QtCore (QObject/QThread/pyqtSignal) and import the module directly.
- ADD A FEATURE = ADD A MIXIN: create modules/<feature>.py with a *Mixin class,
  then add it to CommandBridgeV4's base list in ui/window.py (~line 49) and import it.
- CONSOLE COLOUR: prefix lines with [DANGEROUS] (red) / [WARNING] (orange), or use
  console.append_html() for custom colours. Plain append_ansi() strips ANSI.
- DON'T BLOCK THE UI: anything slow (network loops, external scanners) goes in a
  QThread worker (copy the _SslScanWorker / _ExternalsWebReconWorker pattern) and
  keep a reference on self so it isn't GC'd.
- COMMAND TEMPLATES: prefer self.command_registry + a right-click editor for any
  command a tester might want to tweak. Persist with save_custom_commands().
- OUTPUT FILES: write into self.output_dir; call self.refresh_file_list() so the
  file panel updates. The Externals run cleans old report files at the start of
  run_externals_workflow() — add new report filenames to that cleanup list.
- TAB INDEX: Console tab is index 5 (self.tab_widget.setCurrentIndex(5)).
